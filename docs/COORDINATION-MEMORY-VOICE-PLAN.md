## Amendment 2026-09-29 — contract corrections before step-2/3 repair

Audit of the partial implementation against this plan found contract defects that must be resolved inside the steps below; step IDs, file ownership and acceptance criteria are unchanged.

- **Decision gating uses shape only.** `decide` must not gate prerequisite or retry on `Work.status` display strings (`Queued`, `Working`, `Completed`, `Failed`, `Cancelled`, `Waiting`, `Needs confirmation`, `Stopping`). The partial step-2 code compares them to `verified`/`running`/`pending`, so prerequisite decisions always clarify and retry never gates. Composition validates structure only (a non-independent relationship requires a referenced task; an answer requires a pending question ID); prerequisite and retry blocking is enforced by the dialogue state in step-4 via `canExecute` and revision/attempt-bound verified facts.
- **Source provenance is derivable.** `CuaDialogueState.Source` carries capture ID, owning TranscriptHandoff ID, ASR revision and consumed word ranges — nothing that requires new identity in `JevVoiceCore`. Remove `segmentIDs`; `transcriptRanges` are word offsets into the owning handoff's transcript, the same unit as `CuaExecutorDecision.consumedRange`.
- **One answer model.** An utterance classified as an answer applies `Answer` to the question's owner entry and resumes that intent with a bumped revision; it never creates a separate intent entry. Remove `Relationship.answer` from `add` and remove `Entry.answerQuestionOwnerIntentID`; a `CuaTaskRelationship.answer` decision plus its `questionID` routes to `dialogue.answer`, never `add`.
- **Retry is in-place.** An explicit retry resumes the referenced intent as a fresh attempt after inspecting prior effects; it never creates a separate intent entry. Remove `Relationship.retry` from `add` alongside `.answer`: `.uncertain` intents retry via `retryUncertain` (preserving revision and recorded facts); other non-executing intents retry via `revise` plus a new attempt. Intentional repetition of a request is an independent intent, not a retry relationship.
- **One context channel.** `TranscriptHandoff` carries explicit `contextRevision` and `contextReadSet` only; remove `contextStamp` and the JSON key-path fallback parsing in `SemanticContext.init`. `CuaVoiceRuntime` is the sole producer through the coordinator's `semanticContext` closure.

Three integration obligations added to step-4:

- `makeToolCall`/attempt completion must define which observed evidence produces `verifiedFact` outcomes: observed postconditions bound to the producing attempt and intent revision. A plain `.verified` outcome records no fact and cannot discharge a prerequisite; unsupported readback blocks honestly rather than fabricating one.
- Blocked, uncertain and partial intents are unresolved and count against `unresolvedLimit`; the runtime owns resolving them (cancel, revise or retry) so `add` cannot wedge on accumulated terminal-ambiguous entries.
- The context projection must publish pending questions with their IDs; an `answer` decision binds a `questionID` and cannot route without it.

This amendment revises the accepted step-1 Source/Relationship contracts. The correction stays within step-1 file ownership; apply it alongside the step-2/3 repairs and rerun `CuaDialogueStateTests` before either parallel step is declared PASS.
